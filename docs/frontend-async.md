# 第五阶段：自动跟踪与个人历史

## 当前行为

- 详情页自动加载当前模板的个人记录；页头「我的作品」进入 `/history`，加载跨模板记录。
- 刷新页面从 Java 恢复身份，之后自动恢复历史；切换用户后清空原 scope，并自动加载新用户数据。上传槽位选择仍不恢复。
- 任务受理后立即显示卡片，按钮退出提交中，可继续创建其他任务；历史请求尚未完成时也保留新任务展示。
- 首次从 `GET /api/tasks` 读取最近 100 条及全部未完成任务，去重后倒序显示。查询超过 100 条时仍保留更早的未完成任务，避免刷新漏跟踪。没有更早终态记录的翻页。
- 后续只请求 `GET /api/tasks/{id}` 中的 QUEUED / RUNNING，每轮全部请求结束后约 2 秒继续，最多同时 4 个请求。SUCCEEDED / FAILED 停止查询；无可查询项时无定时器，不持续请求列表。
- 本页没有待处理任务时，在其他标签页／客户端创建的新任务不会主动推送过来；点击「刷新记录」发现新任务。重进页面也会重新加载。

## 查询异常与任务失败

执行失败只根据 Java 返回的 FAILED 判定，显示失败阶段与原因。请求超时、网络／503／非法响应等属于查询异常：

1. 单任务查询失败：保留其上次状态和结果，黄色提示暂停查询，其他任务继续自动更新。
2. 初次历史失败：显示请求异常及恢复入口，不把它伪装成空历史。
3. 刷新历史失败：已有记录保留；暂停自动跟踪，点击恢复查询后重新读取。
4. 恢复查询会取消旧查询、重新加载历史，成功后清除查询错误并继续跟踪未完成任务。
5. 每个请求 15 秒超时，取消请求并显示可恢复的反馈，不无限自动重试失败项。
6. 会话 401 或响应归属不一致：停止旧 scope、清空其任务视图，重新确认身份，不将任务标为失败。

红色「制作失败」与黄色「查询暂时不可用」表达不同情况。前端不根据经过时间伪造阶段，阶段、开始／结束时间和结果仍来自 Java 持久化记录。

## 生命周期实现

`frontend/src/lib/tasks.ts` 的 createTaskFeed 同时用于页面和测试，React 通过 useSyncExternalStore 订阅。创建控制器不会联网；页面 effect 启动，清理时停止。scope key 包含用户 ID、身份 generation、标准模板 ID（历史页为 all）。

控制器保存每次请求实例与 AbortController，同时检查活跃状态和当前请求归属；卸载、切换用户或手动恢复时取消相关请求和定时器。即使旧 Promise 忽略 abort 后迟到，也不会覆盖新记录。单个任务查询也核对响应 ID／用户／模板。合并历史和任务快照时拒绝更旧时间戳，比较保留 Java 时间戳的微秒精度，终态不回退为处理中。

新建任务后重新读取历史，先前早于受理的列表请求失效，已受理任务不会被旧列表清除。个人任务没有写到 localStorage，刷新后以 Java 为准；已有身份跨标签通知继续使用原先的 storage 事件。

## 页面手动检查

1. 选择小陈，打开一个模板，已有记录应自动出现，无需点刷新；打开「我的作品」能看到跨模板记录。
2. 上传示例图，每阶段 3000ms，全部成功。开始制作后不点刷新，应看到排队／阶段自动更新，最后显示图片。
3. 连续创建一个成功、一个模拟生成失败的任务，状态各自独立；失败后结果整理不启动。结束后提示自动查询已停止。
4. 处理中刷新浏览器，应自动恢复并继续更新；离开到模板列表，后台仍继续，重新进入详情／历史应恢复。
5. 处理中切到小林，原用户记录消失，新用户记录自动加载；切回小陈自动恢复，不需手动查询。
6. 浏览器 Network 过滤 `/api/tasks`：初次一个列表请求，后续只有未完成 ID 的 GET；终态之后不再轮询它，全部结束后不再有自动请求。React 开发模式可因 effect 校验多一次已取消的初始化请求，生产容器不据此伪造测试通过。
7. 请求异常检查（可用浏览器开发工具，不关 Java）：给 `/api/tasks/*` 请求设置阻断，保持一个较长任务；应显示黄色查询异常，原状态保留，不能变为制作失败。关闭阻断后点击恢复查询，应读回真实状态。只阻断列表 `/api/tasks` 可检查初次／手动刷新失败。Chrome 不同版本的阻断方式可能不同，也可用离线模式检查整体网络异常。
8. 小屏与键盘检查：菜单可用、用户选择可操作，按钮可聚焦，结果图和错误提示不产生横向溢出。

以上是待执行／待反馈的浏览器清单。本轮完成控制器与 HTTP 验证，不声称已完成全部浏览器操作。

21 个前端测试全部通过。其中 14 个新增用例运行实际控制器，使用可控时钟和 Promise，覆盖自动恢复、多任务独立、终态停止、无任务无轮询、单项／列表异常、手动恢复、取消及迟到响应、用户 scope、401／归属校验、15 秒超时、最多 4 个并发与终态／旧时间戳保护。其余为一个接口数据校验和六个上传状态测试；移除了已不用于页面的旧状态辅助函数及其三个冗余测试。没有新增 npm 依赖。

可重复的真实控制器 + HTTP 检查可以完全在容器内运行：

```bash
docker compose cp frontend/src/lib/tasks.ts frontend:/tmp/xiaoying-tasks.ts
docker compose cp tools/smoke-task-feed.mjs frontend:/tmp/xiaoying-smoke-task-feed.mjs
docker compose exec -T -e TASK_MODULE_URL=file:///tmp/xiaoying-tasks.ts frontend node --experimental-default-type=module /tmp/xiaoying-smoke-task-feed.mjs
```

也可用本机 Node 22.18+ 执行 `node --experimental-default-type=module tools/smoke-task-feed.mjs`；默认连接本机 3000。容器命令不依赖宿主机 Node，并且不安装新依赖。

脚本会给小陈保留两条非个人示例任务、结束时退出测试会话。它直接使用实际前端查询控制器，通过正式同源代理与 Java / MySQL 交互，故意让一次单任务查询抛出请求异常，验证上次状态保留、另一任务继续更新、手动恢复、终态后无新增查询、新 scope 自动加载和用户隔离。本轮脚本输出 PASS，正式三个服务健康，专用测试 MySQL 已停止。

这不是浏览器或 React 挂载测试：能证明实际控制器和接口协作，不能单独证明按钮、布局、浏览器焦点或所有 React 行为。用户第四阶段反馈仍只对应其手动检查范围；第五阶段新增 UI 待试用。云端 CI 待本阶段 push 后核对。

## 交付与边界

本轮不新增业务表或依赖，无需 npm install 或增量 SQL；更新时 `docker compose up --build -d --wait` 即可。日常仍三个服务，mysql-check 仅在 checks profile 运行，512MB tmpfs，无宿主机端口、无应用数据卷，停止后重新初始化。

测试通过后按阶段提交，Git 命令由助手在阶段收尾给出，用户自行 commit / push。文档随每阶段同步，不将 CI 截图扩大成全量验收。

后端无幂等、自动重试、执行中续跑／集群／容量限制等边界沿用后端说明。前端无跨标签任务推送、不无限自动重试查询异常、不提供更早终态记录分页。数据库／素材持久性依赖保留应用数据卷。回滚到前一阶段应用时保留数据卷和表，本次只修改查询范围与页面，无数据迁移；回滚仍需先记录 commit、备份并核对应用兼容性。
